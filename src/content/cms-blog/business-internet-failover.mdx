<script>
(function () {
  var root = document.getElementById('spenza-failover-calculator');
  if (!root) return;

  var sitesEl = root.querySelector('#spz-sites');
  var typeEl = root.querySelector('#spz-type');
  var hoursEl = root.querySelector('#spz-hours');
  var sessionsEl = root.querySelector('#spz-sessions');

  var fleetCostEl = root.querySelector('#spz-fleet-cost');
  var siteCostEl = root.querySelector('#spz-site-cost');
  var idleEl = root.querySelector('#spz-idle');
  var activeEl = root.querySelector('#spz-active');
  var poolEl = root.querySelector('#spz-pool');
  var fixedEl = root.querySelector('#spz-fixed');
  var savingEl = root.querySelector('#spz-saving');

  var usagePerHour = {
    retail: 0.25,
    qsr: 0.45,
    office: 1.20,
    clinic: 0.80
  };

  function money(value) {
    return new Intl.NumberFormat('en-US', {
      style: 'currency',
      currency: 'USD',
      maximumFractionDigits: 0
    }).format(value);
  }

  function dataLabel(gb) {
    if (gb < 1) return Math.round(gb * 1000) + ' MB';
    if (gb < 100) return gb.toFixed(1) + ' GB';
    return Math.round(gb).toLocaleString('en-US') + ' GB';
  }

  function calculate() {
    var sites = Math.max(1, Number(sitesEl.value) || 1);
    var hours = Math.max(0, Number(hoursEl.value) || 0);
    var type = typeEl.value;
    var sessions = sessionsEl.value === 'yes';

    // Same simple assumptions used in the earlier model:
    // 2 MB/site/day idle overhead
    // site-type active usage per outage hour
    // +15% if sessions must survive switchover
    // 25% pool headroom
    // $2/site/month + $5/pooled GB
    // fixed comparison = $10/site/month
    var annualIdleGb = (sites * 2 * 365) / 1000;
    var annualActiveGb = sites * hours * usagePerHour[type] * (sessions ? 1.15 : 1);
    var annualTotalGb = annualIdleGb + annualActiveGb;
    var monthlyPoolGb = Math.max(1, Math.ceil((annualTotalGb * 1.25) / 12));

    var annualPooledCost = (sites * 2 * 12) + (monthlyPoolGb * 5 * 12);
    var annualFixedCost = sites * 10 * 12;
    var savings = annualFixedCost - annualPooledCost;
    var savingsPct = annualFixedCost > 0 ? (savings / annualFixedCost) * 100 : 0;

    fleetCostEl.textContent = money(annualPooledCost);
    siteCostEl.textContent = money(annualPooledCost / sites) + ' per site / year';
    idleEl.textContent = dataLabel(annualIdleGb);
    activeEl.textContent = dataLabel(annualActiveGb);
    poolEl.textContent = monthlyPoolGb.toLocaleString('en-US') + ' GB';
    fixedEl.textContent = money(annualFixedCost);

    if (savings >= 0) {
      savingEl.textContent = money(savings) + ' lower than the fixed-plan model (' + Math.round(savingsPct) + '%)';
    } else {
      savingEl.textContent = money(Math.abs(savings)) + ' higher than the fixed-plan model';
    }
  }

  [sitesEl, typeEl, hoursEl, sessionsEl].forEach(function (el) {
    el.addEventListener('input', calculate);
    el.addEventListener('change', calculate);
  });

  calculate();
})();

<h3 class="wp-block-heading"><strong>The Cost Stack: Hardware, Plans, Licenses</strong></h3>



<p class="wp-block-paragraph">A per-site cellular backup carries four costs, and connectivity is the one your commercial model can change. Business backup plans typically run $30 to $50 per month for 10 to 20GB of LTE or 5G data. Hardware spans a wider range: dual-WAN routers with cellular start around $129 at consumer grade, cloud-managed mid-range units run a few hundred, and enterprise cellular routers pass $2,500 and add mandatory management licenses. Installation is a one-off that varies with cabling and rack access. Support is an allowance for quarterly testing and the occasional on-site visit.</p>



<p class="wp-block-paragraph">Hardware and installation cost the same whether you buy one plan per site or pool data across the fleet. Spenza sells no routers, so the ranges above are the published market, not a price list we defend. That leaves the plan line, and at fleet scale it is the only line that compounds.</p>



<h3 class="wp-block-heading"><strong>Why Pooled Data Changes the Math at Scale</strong></h3>



<p class="wp-block-paragraph">A backup connection does almost nothing almost all the time. Its data usage is near zero except during an outage, plus a small constant overhead of health-check probes and management-tunnel traffic. Outages are rare, and across a fleet they are largely uncorrelated: an ISP delivering 99.9% availability still leaves each site dark for roughly eight to nine hours a year, but those hours land at different sites in different weeks.</p>



<p class="wp-block-paragraph">The standard commercial model prices every site as if it might fail over tomorrow: a fixed monthly plan per location, bought 100 times for 100 sites. Fixed per-site plans are the incumbent revenue model, which is why no carrier will make this argument against its own pricing.</p>



<p class="wp-block-paragraph">A pooled model sizes one shared data allowance for the fleet&#8217;s realistic concurrent-failover exposure plus idle overhead. Sites that never fail over stop paying for capacity they never use. Four steps keep the pool honest:</p>



<ol class="wp-block-list">
<li>Measure one site&#8217;s idle usage for a week. Probes and cloud-management tunnels consume real data every month, and that figure belongs in the model, not in a footnote.</li>



<li>Estimate expected outage hours per site per year from your primary ISP&#8217;s actual track record, not its SLA.</li>



<li>Multiply outage hours by your site type&#8217;s active-failover consumption (sizing anchors below).</li>



<li>Add headroom for a regional event in which several sites fail over at once.</li>
</ol>



<p class="wp-block-paragraph">Two regimes, two parts of the model: pooling absorbs everyday uncorrelated outages, and the headroom step plus carrier diversity cover the rare regional event where failures arrive together.</p>



<div style="background-color: #fff4e5; border-left: 5px solid #FF9800; padding: 1.4em 1.6em; margin: 2em 0; border-radius: 6px; font-family: Arial, sans-serif; box-shadow: 0 2px 5px rgba(0,0,0,0.05);">
<div style="color: #ff9800; font-size: 1.05em; font-weight: bold; margin-bottom: 0.9em;">Key Takeaway</div>
<p style="margin: 0; line-height: 1.6;">At typical business rates of <span style="font-weight: bold;">$30 to $50 per site per month</span>, 100 sites can carry <span style="font-weight: bold;">$36,000 to $60,000 per year</span> in fixed plan costs, much of it paying for data that never gets consumed. A <span style="font-weight: bold;">pooled data allowance</span> sized around realistic concurrent usage can preserve the protection you need while eliminating unnecessary capacity and reducing wasted spend.</p>
</div>

<h3 class="wp-block-heading"><strong>What Breaks When You Fail Over (and the Fixes)</strong></h3>



<p class="wp-block-paragraph">On a warm failover your public IP changes, and three things follow. VPN tunnels drop and must re-establish. Calls drop and desk phones re-register over SIP (the signaling protocol behind VoIP phones), so a call in progress dies even though the next one works. Inbound access rules, the port-forwards that let remote systems reach the site, need configuring against both WAN identities, or remote access quietly fails until someone notices. Any page that implies switchover is free has not run one.</p>



<p class="wp-block-paragraph">The fixes, ranked by coverage: an SD-WAN overlay or bonded tunnel preserves sessions outright. Shorter SIP registration timers and application-level retry cover most of the remainder. For card processing, modern POS terminals retry gracefully when the gap is seconds rather than minutes, which is why warm mode is usually enough for retail and bonded mode earns its cost where sessions carry revenue.</p>



<p class="wp-block-paragraph">Failback needs hysteresis, a deliberate settle time before traffic returns. A flapping primary that triggers failover every few minutes is worse than a dead one, so health checks need failure thresholds on both directions of the switch.</p>



<div style="background-color: #fff4e5; border-left: 5px solid #FF9800; padding: 1.4em 1.6em; margin: 2em 0; border-radius: 6px; font-family: Arial, sans-serif; box-shadow: 0 2px 5px rgba(0,0,0,0.05);">
<div style="color: #ff9800; font-size: 1.05em; font-weight: bold; margin-bottom: 0.9em;">Expert Tip</div>
<p style="margin: 0; line-height: 1.6;"><span style="font-weight: bold;">Test your backup connection every quarter.</span> Temporarily pull the primary connection and verify that critical services such as <span style="font-weight: bold;">POS systems, phones, and VPNs</span> recover as expected. An untested backup has an unknown probability of working, and a live outage is the worst possible time to discover that something is misconfigured.</p>
</div>

<h2 class="wp-block-heading"><strong>Single-Carrier Backup Is a Second Point of Failure</strong></h2>



<p class="wp-block-paragraph">A backup is only a backup if it shares no failure domain with the thing it protects. The logic applies twice: between your primary and your backup, and across the backup itself.</p>



<h3 class="wp-block-heading"><strong>The Failure-Domain Checklist</strong></h3>



<p class="wp-block-paragraph">Four failure domains decide whether a backup will actually be there:</p>



<ul class="wp-block-list">
<li><strong>Physical path: </strong>Cellular runs on separate infrastructure from cable and fiber, which is the standard argument for cellular backup. It is correct, and it is where most vendor pages stop.</li>



<li><strong>Power: </strong>A failover router on the same unprotected outlet as everything else dies with the site. A UPS (uninterruptible power supply, the battery that rides out a blackout) on the failover path is a one-line requirement most pages omit.</li>



<li><strong>Carrier core: </strong>A single-carrier backup makes that carrier a new single point of failure across every site at once. Major single-carrier outages are documented, recurring events, not edge cases.</li>



<li><strong>Congestion: </strong>During a regional primary-ISP outage, every affected business fails over onto the same cells at the same time. Multi-carrier selection and business-tier data priority are the honest mitigations. Nothing grants immunity.</li>
</ul>



<h3 class="wp-block-heading"><strong>What the Payments Outage in Canada Proved</strong></h3>



<p class="wp-block-paragraph">On 8 July 2022, the Rogers network failed nationwide and took Interac debit processing down with it, because Canada&#8217;s payment infrastructure rode on one carrier. Stores sold for cash or not at all for most of a day. Interac&#8217;s response is the instructive part: it<a href="https://www.interac.ca/en/content/news/interac-statement-on-rogers-outage/" target="_blank" rel="noreferrer noopener"> added a secondary network carrier</a> so that no single carrier failure could take payments down again.</p>



<p class="wp-block-paragraph">The pattern is not Canadian. On 22 February 2024, a misconfigured network change took AT&amp;T&#8217;s mobile network down across all 50 US states for at least 12 hours. The<a href="https://docs.fcc.gov/public/attachments/DOC-404154A1.pdf" target="_blank" rel="noreferrer noopener"> FCC&#8217;s post-incident report</a> counts more than 92 million blocked voice calls and over 25,000 failed attempts to reach 911.</p>



<p class="wp-block-paragraph">If payments, alarms, or phones ride your backup, carrier diversity decides whether you bought a backup or a second copy of the same risk. Bonded multi-carrier bundles already solve this for a single store. A fleet needs the same diversity without buying it one store at a time, which is exactly what pooled multi-carrier plans are for.</p>

<h2 class="wp-block-heading"><strong>How Much Data Does Failover Actually Use?</strong></h2>



<p class="wp-block-paragraph">Almost none, until it uses a lot. In normal operation, a backup SIM carries only idle overhead: health-check probes, monitoring, and the always-on management tunnel of a cloud-managed router.</p>



<p class="wp-block-paragraph"><strong>For the calculator, we model typical idle usage at 2 MB per site per day, or approximately 61 MB per site per month and 0.73 GB per site per year.</strong> This is deliberately small compared with active failover consumption.</p>



<p class="wp-block-paragraph">During an outage, usage jumps to whatever the site actually runs through the backup connection. A QSR supporting POS, kitchen systems, online ordering, delivery platforms, and other critical cloud traffic will consume substantially more than an idle connection. That is why failover capacity should be sized by <strong>site type, outage exposure, and the workloads that must stay online</strong>, rather than using a single fleet-wide data allowance.</p>



<div style="background-color: #fff4e5; border-left: 5px solid #FF9800; padding: 1.4em 1.6em; margin: 2em 0; border-radius: 6px; font-family: Arial, sans-serif; box-shadow: 0 2px 5px rgba(0,0,0,0.05);">
<div style="color: #ff9800; font-size: 1.05em; font-weight: bold; margin-bottom: 0.9em;">Example</div>
<p style="margin: 0; line-height: 1.6;">A <span style="font-weight: bold;">100-site retail fleet</span> expecting <span style="font-weight: bold;">eight outage hours per site per year</span> accumulates about <span style="font-weight: bold;">800 active-failover site-hours annually</span>. Card authorization and back-office synchronization are relatively light workloads, typically using around <span style="font-weight: bold;">1 to 5 GB per month per register</span> even during active use, so the data pool required to cover those failover periods can remain relatively small. <br /><br />The same <span style="font-weight: bold;">800 failover hours</span> at an office where employees run full video-meeting workloads over the backup connection represents a completely different requirement. Video conferencing can consume <span style="font-weight: bold;">several gigabytes per user per day</span>, making the appropriate backup data pool substantially larger. <br /><br /><span style="font-weight: bold;">The lesson:</span> size the failover pool around the actual workload, not simply the number of sites or expected outage hours.</p>
</div>
