<h2 class="wp-block-heading"><strong>Spenza MCP: Powering AI Agents for Telecom Operations</strong></h2>



<figure class="wp-block-video"><video height="1080" style="aspect-ratio: 1920 / 1080;" width="1920" autoplay controls muted poster="/wp-content/uploads/2026/09/image-5.png" src="/wp-content/uploads/2026/09/Spenza_MCP_Server_Launch.mp4" playsinline></video></figure>



<p class="wp-block-paragraph">The Spenza MCP Server is live at <a href="https://mcp.spenza.com/" target="_blank" rel="noopener">mcp.spenza.com</a>. Connect it to Claude, ChatGPT, Cursor, VS Code or any MCP client, and the model can do what the <a href="https://docs.spenza.com/" target="_blank" rel="noopener">Spenza Partner API</a> does: list and inspect SIMs, provision eSIMs, buy and schedule plans, pull invoices, register webhooks, send SMS, and 70-odd other operations against your live account.</p>



<p class="wp-block-paragraph">Most telecom MCP servers available today are documentation search. It helps an agent write the integration, not run it. <strong>Spenza&#8217;s </strong>server executes. Ask &#8220;<strong>which SIMs on the fleet are past 80% of their data allowance this cycle, and pause data on the ones assigned to contractors</strong>&#8220;, and the assistant lists the SIMs, checks usage, and calls the service-state tool for each one, with you approving every write.</p>



<p class="wp-block-paragraph">This post covers what the server exposes, how to connect it in under two minutes, five workflows we run on our own account, and how to call it from code. There is an FAQ at the end for the questions we keep getting.</p>



<h2 class="wp-block-heading"><strong>Why we built it</strong></h2>



<p class="wp-block-paragraph">Connectivity operations still run on dashboards, tickets and CSV exports. An ops lead who wants to know which lines are idle, who is about to overrun a plan, or why a webhook stopped delivering opens three screens, exports two files, and reconciles them in a spreadsheet. If the answer calls for action, someone raises a ticket and a second person clicks through the console.</p>



<p class="wp-block-paragraph">We built the <a href="https://docs.spenza.com/introduction" target="_blank" rel="noopener">Partner API</a> so that partners could put that work in their own systems. The API is consistent by design: one response envelope, one pagination scheme, one error taxonomy, idempotency keys on writes, and one async pattern for anything that takes real-world time. That consistency is exactly what a language model needs to use an API well, so wrapping it as an MCP server was a short step.</p>



<p class="wp-block-paragraph">The result changes who can operate the platform. An analyst who has never opened the API reference can ask a question in plain English and get an answer sourced from live data. A support engineer can resolve a &#8220;my eSIM won&#8217;t activate&#8221; ticket by asking the assistant to check the provisioning transaction, read the failure reason, and re-fetch the activation QR. A finance lead can pull last quarter&#8217;s invoices into a summary without waiting on engineering.</p>



<p class="wp-block-paragraph">For <a href="https://codiant.com/technologies/hire-ai-developers/" data-type="link" data-id="https://codiant.com/technologies/hire-ai-developers/">AI developers</a> it changes something else: an agent you build on Claude, OpenAI or any MCP-aware framework can now hold a Spenza account as a capability, not a bespoke integration. The <a href="/" target="_blank" rel="noopener">Agentic MVNO</a> we have been describing, three hubs plus the AI agents that run them, needs a surface that agents can call directly. This server is that surface.</p>



<h2 class="wp-block-heading"><strong>What the server exposes</strong></h2>



<p class="wp-block-paragraph">The server publishes 79 tools that map one-to-one onto the Partner API: 39 reads and 40 writes across 15 resource groups. Tool names follow a verb_noun convention (<code>list_sims</code>, <code>get_sim_usage</code>, <code>provision_esim</code>), so a model can guess most of them before it reads the schema.</p>

<p class="wp-block-paragraph">Every tool carries the same guardrails the API does. Writes take an idempotency key, so a retried call replays instead of repeating. Anything slow (eSIM provisioning, a Stripe checkout, a port-in) returns a <code>transactionId</code> immediately, and the assistant polls <code>get_async_transaction_status</code> until it resolves. Errors come back as a typed code (<code>SIM_NOT_FOUND</code>, <code>RATE_LIMITED</code>, <code>VALIDATION_ERROR</code>) rather than a message the model has to parse. See <a href="https://docs.spenza.com/core-concepts" target="_blank" rel="noopener">Core Concepts</a> and <a href="https://docs.spenza.com/errors" target="_blank" rel="noopener">Errors</a> for the full contract.</p>



<p class="wp-block-paragraph">The tool descriptions also carry the sharp edges the docs call out, because a model reads descriptions before it reads reference pages. <code>cancel_subscription</code> says it always cancels at the end of the billing period. <code>purchase_plan_async</code> says to give exactly one of <code>activateNow</code> or <code>scheduleDate</code>. <code>update_sim_service_state</code> says it charges an action fee on success. Those lines exist so an assistant does not have to learn them by failing.</p>



<h2 class="wp-block-heading"><strong>Connect in under two minutes</strong></h2>



<p class="wp-block-paragraph">The server is remote and hosted by Spenza, so there is nothing to install. It speaks MCP over Streamable HTTP at <code>https://mcp.spenza.com/mcp</code> and authenticates with the same API key and secret your partner account already uses for the <a href="https://docs.spenza.com/authentication" target="_blank" rel="noopener">Partner API</a>. Credentials are issued when your account is set up; if you do not have a pair, <a href="https://docs.spenza.com/support" target="_blank" rel="noopener">ask support</a>.</p>



<p class="wp-block-paragraph">Keep the key and secret in environment variables. Every snippet below reads them from <code>SPENZA_API_KEY</code> and <code>SPENZA_API_SECRET</code>.</p>



<h3 class="wp-block-heading"><strong>Claude Code</strong></h3>



<pre class="wp-block-code"><code>claude mcp add --transport http spenza https://mcp.spenza.com/mcp \
  -H "X-Spenza-Api-Key: $SPENZA_API_KEY" \
  -H "X-Spenza-Api-Secret: $SPENZA_API_SECRET" \
  --scope user</code></pre>



<p class="wp-block-paragraph">Run <code>/mcp</code> inside Claude Code to confirm the server shows as connected, then ask it something: &#8220;how many SIMs on this account are unassigned?&#8221;</p>



<h3 class="wp-block-heading"><strong>Claude (web and desktop)</strong></h3>



<p class="wp-block-paragraph">Open Settings, choose Connectors, then Add custom connector. <p class="wp-block-paragraph">Each of these is a single prompt. The tool chain underneath is what the assistant actually calls, in order, and it is the same chain you would write by hand against the API.</p>



<h3 class="wp-block-heading"><strong>1. Usage triage before the cycle closes</strong></h3>



<blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow">
<p class="wp-block-paragraph"><strong>Show me every active SIM past 80% of its data allowance this cycle, with the assigned user and department. Then pause data on any that belong to contractors.</strong></p>
</blockquote>



<ol class="wp-block-list">
<li><code>list_sims</code> with <code>status: ACTIVE</code>, paged at 100</li>



<li><code>get_sim_usage</code> for each SIM, comparing <code>data.used</code> to the plan allowance</li>



<li><code>get_user</code> for the assignee to read the department</li>



<li><code>update_sim_service_state</code> with <code>data: false</code> on the contractor lines, one confirmation per SIM</li>
</ol>



<p class="wp-block-paragraph">The first three steps are reads and run without prompts. Step four charges an action fee, and the tool description says so, which is why every client we have tested stops and asks before running it.</p>



<h3 class="wp-block-heading"><strong>2. Provision an eSIM for a new hire</strong></h3>



<blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow">
<p class="wp-block-paragraph"><strong>Provision an eSIM for Priya Nair&#8217;s new iPhone, IMEI 356938035643809, on the AT&amp;T 5GB plan, activate today, and give me the activation QR.</strong></p>
</blockquote>



<figure class="wp-block-image aligncenter size-large is-resized"><img decoding="async" width="1024" height="576" src="/wp-content/uploads/2026/09/image-7-1024x576.png" alt="Provision an eSIM for a new hire - Mermaid Diagram " class="wp-image-22571" style="width:777px;height:auto" srcset="/wp-content/uploads/2026/09/image-7-1024x576.png 1024w, /wp-content/uploads/2026/09/image-7-300x169.png 300w, /wp-content/uploads/2026/09/image-7-768x432.png 768w, /wp-content/uploads/2026/09/image-7-1536x864.png 1536w, /wp-content/uploads/2026/09/image-7.png 1672w" sizes="(max-width: 1024px) 100vw, 1024px" /></figure>



<p class="wp-block-paragraph">Provisioning is asynchronous on the API, so the assistant polls rather than assuming success. If the carrier rejects the IMEI or the ZIP code has no number available, the failure reason arrives on the status call and the assistant reports it instead of handing over a QR that will never activate.</p>



<h3 class="wp-block-heading"><strong>3. A webhook stopped delivering</strong></h3>



<blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow">
<p class="wp-block-paragraph"><strong>Our inbound SMS webhook stopped firing yesterday afternoon. Find out why and get the missed events redelivered.</strong></p>
</blockquote>



<ol class="wp-block-list">
<li><code>list_webhooks</code> to find the registration and confirm it is still <code>active</code></li>



<li><code>list_webhook_deliveries</code> to see the attempts, newest first, and read the failure status codes</li>



<li><code>test_webhook</code> to send a signed synthetic event and check the endpoint is reachable now</li>



<li><code>redeliver_webhook_delivery</code> for each failed attempt, using the stored original payload</li>
</ol>



<p class="wp-block-paragraph">The delivery log records the HTTP status of every attempt, so a 401 from a rotated token on your side or a 5xx from a bad deploy shows up in the first pass. Redelivery replays the stored original payload rather than regenerating the event, and it runs on a queue, so the assistant checks the deliveries list again a minute later to confirm the retries landed.</p>



<h3 class="wp-block-heading"><strong>4. Month-end billing summary</strong></h3>



<blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow">
<p class="wp-block-paragraph"><strong>Summarise September invoices by status with totals, list anything open for more than 30 days, and tell me the prepaid balance.</strong></p>
</blockquote>



<ol class="wp-block-list">
<li><code>list_invoices</code> with <code>from: 2026-09-01</code> and <code>to: 2026-09-30</code></li>



<li><code>get_invoice</code> for the open ones, to read due dates and line items</li>



<li><code>get_credit_balance</code></li>
</ol>



<p class="wp-block-paragraph">If you then say &#8220;top up $500&#8221;, the assistant calls <code>create_credit_top_up</code>, which returns a hosted Stripe checkout link. A human completes the payment. The model never holds a card number, and the top-up only completes when Stripe&#8217;s webhook fires.</p>



<h3 class="wp-block-heading"><strong>5. Move a group to a new plan next cycle</strong></h3>



<blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow">
<p class="wp-block-paragraph"><strong>Move every SIM in the Field Sales group to the 10GB plan, effective the first of next month.</strong></p>
</blockquote>



<ol class="wp-block-list">
<li><code>get_sim_group</code> to read the membership</li>



<li><code>list_plans</code> to resolve the exact <code>productName</code></li>



<li><code>purchase_plan_async</code> per SIM with <code>scheduleDate</code> set to the first of the month</li>



<li><code>get_async_transaction_status</code> to confirm each purchase is scheduled</li>
</ol>



<p class="wp-block-paragraph">Because writes accept an idempotency key, a retry after a timeout does not schedule the plan twice. That is the difference between an assistant you let touch 12 SIMs and one you let touch 1,200.</p>



<h2 class="wp-block-heading"><strong>For builders: call it from code</strong></h2>



<p class="wp-block-paragraph">The chat clients above are the fastest way to try the server. The more durable use is an agent you own: a nightly usage check that posts to Slack, a support bot that resolves eSIM tickets, an onboarding flow that provisions a line the moment HR creates an employee. All three major paths work today.</p>



<h3 class="wp-block-heading"><strong>Anthropic Messages API</strong></h3>



<p class="wp-block-paragraph">The <a href="https://platform.claude.com/docs/en/agents-and-tools/mcp-connector" target="_blank" rel="noopener">MCP connector</a> takes the server URL and a bearer token. Exchange your key and secret for a token at <code>POST /api/v1.1/auth/token</code> (it lasts an hour, so refresh it in your job), then pass it as <code>authorization_token</code>. The <code>mcp_toolset</code> block below disables the money-moving and destructive tools so this particular agent can only read and report:</p>



<pre class="wp-block-code"><code>import anthropic, os

client = anthropic.Anthropic()

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    betas=&#91;"mcp-client-2025-11-20"],
    mcp_servers=&#91;{
        "type": "url",
        "url": "https://mcp.spenza.com/mcp",
        "name": "spenza",
        "authorization_token": os.environ&#91;"SPENZA_TOKEN"],
    }],
    tools=&#91;{
        "type": "mcp_toolset",
        "mcp_server_name": "spenza",
        "configs": {
            "purchase_plan": {"enabled": False},
            "purchase_plan_async": {"enabled": False},
            "cancel_subscription": {"enabled": False},
            "create_credit_top_up": {"enabled": False},
            "delete_user": {"enabled": False},
            "delete_webhook": {"enabled": False},
        },
    }],
    messages=&#91;{
        "role": "user",
        "content": "List every active SIM above 80% of its data allowance this cycle. Return ICCID, assignee, used GB and allowance GB as a table.",
    }],
)

print(response.content&#91;-1].text)</code></pre>



<p class="wp-block-paragraph">With 79 tools on one server, set <code>default_config: {"defer_loading": true}</code> and pair it with Anthropic&#8217;s <a href="https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool" target="_blank" rel="noopener">tool search tool</a> so only the relevant descriptions enter the context on each turn.</p>



<h3 class="wp-block-heading"><strong>OpenAI Responses API</strong></h3>



<p class="wp-block-paragraph">The <a href="https://developers.openai.com/api/docs/guides/tools-connectors-mcp" target="_blank" rel="noopener"><code>mcp</code> tool type</a> works the same way. Here <code>require_approval</code> waives approval for the read tools and keeps it for every write, so your application sees an <code>mcp_approval_request</code> before anything changes on the account:</p>

READ_ONLY = &#91;
    "list_sims", "get_sim", "get_sim_usage", "list_subscriptions",
    "list_invoices", "get_invoice", "get_credit_balance",
    "list_orders", "list_users", "get_user", "get_async_transaction_status",

resp = client.responses.create(
    model="gpt-6-astra",
    tools=&#91;{
        "type": "mcp",
        "server_label": "spenza",
        "server_description": "Spenza connectivity: SIMs, eSIM, plans, billing, webhooks.",
        "server_url": "https://mcp.spenza.com/mcp",
        "authorization": os.environ&#91;"SPENZA_TOKEN"],

print(resp.output_text)</code></pre>



<h3 class="wp-block-heading"><strong>Direct MCP client (TypeScript)</strong></h3>



<p class="wp-block-paragraph">If you run your own agent loop, or you want the API key and secret headers rather than a bearer token, connect with the <a href="https://github.com/modelcontextprotocol/typescript-sdk" target="_blank" rel="noopener">MCP TypeScript SDK</a> and call tools yourself. This is also the path for n8n, LangGraph, or a cron job that never talks to a model at all:</p>



<pre class="wp-block-code"><code>import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";

const transport = new StreamableHTTPClientTransport(
  new URL("https://mcp.spenza.com/mcp"),
  {
    requestInit: {
      headers: {
        "X-Spenza-Api-Key": process.env.SPENZA_API_KEY!,
        "X-Spenza-Api-Secret": process.env.SPENZA_API_SECRET!,
      },
    },
  },
);

const client = new Client({ name: "fleet-watch", version: "1.0.0" });
await client.connect(transport);

const { tools } = await client.listTools();
console.log(`${tools.length} tools`); // 79

const usage = await client.callTool({
  name: "get_sim_usage",
  arguments: { iccid: "8901260123456789012", history: true },
});
console.log(usage.content);</code></pre>



<p class="wp-block-paragraph">The same transport object plugs into Anthropic&#8217;s client-side MCP helpers (<code>mcpTools</code> with the tool runner) or OpenAI&#8217;s Agents SDK, so you can start with a hand-rolled loop and hand the tool list to a model later without changing the connection.</p>



<h2 class="wp-block-heading"><strong>Security and guardrails</strong></h2>



<figure class="wp-block-image aligncenter size-large is-resized"><img decoding="async" width="1024" height="576" src="/wp-content/uploads/2026/09/image-8-1024x576.png" alt="Security and guardrails in Telecom AI" class="wp-image-22572" style="width:666px;height:auto" srcset="/wp-content/uploads/2026/09/image-8-1024x576.png 1024w, /wp-content/uploads/2026/09/image-8-300x169.png 300w, /wp-content/uploads/2026/09/image-8-768x432.png 768w, /wp-content/uploads/2026/09/image-8-1536x864.png 1536w, /wp-content/uploads/2026/09/image-8.png 1672w" sizes="(max-width: 1024px) 100vw, 1024px" /></figure>



<p class="wp-block-paragraph">An MCP server that can buy plans and cancel subscriptions needs more than a password. Here is how the Spenza server is scoped, and what we recommend on your side.</p>



<p class="wp-block-paragraph"><strong>Account-scoped by construction.</strong> The credentials identify one partner account, and every tool is scoped to it. A SIM on another account returns the same <code>SIM_NOT_FOUND</code> as a nonexistent one; there is no cross-tenant read path for the model to stumble into.</p>



<p class="wp-block-paragraph"><strong>Role tiers carry through.</strong> The API enforces role tiers on the credential the same way the dashboard does; <code>send_sms</code>, for example, requires the Admin tier. Each partner account has one key and secret pair today, so treat that pair as an admin credential and put any read-only restriction in the client, with the allowlists and approvals described below, rather than expecting a lesser key.</p>



<p class="wp-block-paragraph"><strong>Writes are idempotent.</strong> Every write accepts an idempotency key, so a retried tool call replays the original result instead of provisioning a second eSIM or scheduling a second purchase.</p>



<p class="wp-block-paragraph"><strong>Money never passes through the model.</strong> <code>create_credit_top_up</code> returns a hosted Stripe checkout link. The assistant cannot enter a card, and the transaction only completes when Stripe&#8217;s webhook fires. The same applies to plan purchases: they draw on prepaid credit or invoice terms already on the account, never on a payment method the model supplies.</p>



<p class="wp-block-paragraph"><strong>Rate limits are per account, not per client.</strong> The API allows <a href="https://docs.spenza.com/rate-limits" target="_blank" rel="noopener">120 requests per 60-second window</a> by default, with tighter caps on carrier-facing writes: 60 per minute for plan purchase and eSIM provisioning, 30 for SMS and cancellation, 20 for number renewal and top-up, 10 for webhook tests. An assistant that fans out <code>get_sim_usage</code> across 1,000 SIMs will hit the ceiling; the server returns <code>RATE_LIMITED</code> with a <code>Retry-After</code> header, and the well-behaved clients back off on their own.</p>



<p class="wp-block-paragraph">On your side, three habits cover most of the risk:</p>



<ol class="wp-block-list">
<li><strong>Keep approvals on for writes.</strong> Claude, ChatGPT, Cursor and VS Code all ask before a tool call by default. Leave that on for anything that is not a <code>list_</code> or <code>get_</code>. If you build with the API, use the allowlist and approval patterns shown above.</li>



<li><strong>Rotate the credential like a password.</strong> The key and secret are the only thing between the model and the account. Store them in a secrets manager, never in a repo or a shared chat, and <a href="https://docs.spenza.com/security" target="_blank" rel="noopener">ask support to rotate them</a> the moment you suspect exposure.</li>



<li><strong>Log what the assistant did.</strong> The Partner API&#8217;s <a href="https://docs.spenza.com/api-reference/orders-&amp;-transactions/list-orders" target="_blank" rel="noopener">orders</a> and <a href="https://docs.spenza.com/api-reference/orders-&amp;-transactions/list-transactions" target="_blank" rel="noopener">transactions</a> endpoints are the audit trail for anything that cost money; the <a href="https://docs.spenza.com/api-reference/webhooks/list-webhook-deliveries" target="_blank" rel="noopener">webhook deliveries</a> list is the trail for events. An assistant that made a change can also tell you what it called, so ask it.</li>
</ol>



<p class="wp-block-paragraph">One limitation to be clear about: there is no sandbox environment yet. Every call from the MCP server goes to production, the same as the API. A sandbox is on the roadmap; until it ships, test write tools on a SIM you would be comfortable re-provisioning.</p>



<h2 class="wp-block-heading"><strong>Where this fits, and what comes next</strong></h2>



<figure class="wp-block-image aligncenter size-large is-resized"><img loading="lazy" decoding="async" width="1024" height="421" src="/wp-content/uploads/2026/09/image-9-edited-1024x421.png" alt="Spenza’s MCP Server lets AI assistants execute telecom operations" class="wp-image-22574" style="width:666px;height:auto" srcset="/wp-content/uploads/2026/09/image-9-edited-1024x421.png 1024w, /wp-content/uploads/2026/09/image-9-edited-300x123.png 300w, /wp-content/uploads/2026/09/image-9-edited-768x316.png 768w, /wp-content/uploads/2026/09/image-9-edited-1536x631.png 1536w, /wp-content/uploads/2026/09/image-9-edited.png 1672w" sizes="(max-width: 1024px) 100vw, 1024px" /></figure>



<p class="wp-block-paragraph">We describe Spenza as an Agentic MVNO: <a href="/" target="_blank" rel="noopener">TelecomHub</a> for multi-operator connectivity, ControlHub for provisioning, policy and billing, UXHub for the customer-facing surface, and a fourth layer of AI agents that operate the other three. Until now that fourth layer was something we built for ourselves and for individual customers. The MCP server makes it something you can build with whatever model and framework you already run.</p>



<p class="wp-block-paragraph">That matters most for the three kinds of companies we work with. A connected-device OEM can put connectivity operations inside the same assistant its support team already uses, so &#8220;why is this device offline?&#8221; resolves without a telecom specialist. An MSP or connectivity provider can give each account manager an agent that answers billing and usage questions against live data instead of last month&#8217;s export. A software platform embedding mobile lines can let its own product agent provision, suspend and bill without a bespoke integration for every carrier.</p>



<p class="wp-block-paragraph">Three gaps are open today and are the first things on the list:</p>



<ul class="wp-block-list">
<li><strong>A sandbox.</strong> Every call goes to production. A sandbox base URL for the API and the MCP server is the most requested item from early users and is <a href="https://docs.spenza.com/environments-versioning" target="_blank" rel="noopener">on the roadmap</a>.</li>



<li><strong>Port-in submission.</strong> The server exposes eligibility checks and port-in listing; submitting a port-in still goes through the <a href="https://docs.spenza.com/api-reference/numbers-&amp;-port-in/submit-a-port-in" target="_blank" rel="noopener">API endpoint</a> until the confirmation flow is safe enough to hand to a model.</li>



<li><strong>Typed SDKs.</strong> There are <a href="https://docs.spenza.com/sdks" target="_blank" rel="noopener">no official client libraries</a> yet. The OpenAPI spec at <code>docs.spenza.com/openapi.yaml</code> generates a clean client today, and published packages will follow.</li>
</ul>
