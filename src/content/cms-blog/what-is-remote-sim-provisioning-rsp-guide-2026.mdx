<p>Remote SIM provisioning (RSP) is the GSMA-defined way to download, enable, disable and delete mobile operator profiles on an embedded Universal Integrated Circuit Card (eUICC) over the air, so a device can change its connectivity subscription without a new physical SIM. It works only when the device, eUICC, provisioning servers, operator profile and a usable network path all support the operation you ask for.</p>
<p>For a connected-product team the hard part is what happens after the download. A profile can install while the device still cannot reach your application, and an unattended sensor needs a different management model from a phone whose owner taps to approve. This guide explains the components, the three GSMA architectures, the steps a profile goes through, how to handle failure, and the pilot tests to run before a fleet rollout. If you need the basics first, start with <a href="/esim/esim/">what an eSIM is</a>.</p>
<h2 id="what-is-remote-sim-provisioning">What is remote SIM provisioning (RSP)?</h2>
<p>RSP manages the operator credentials that let a compatible device use cellular service. Those credentials arrive as a profile and live inside the eUICC, a secure element built for profile management. RSP changes them through standardized, authenticated operations. It does not replace the modem, create radio coverage or grant a carrier contract. You still need a commercial agreement with an operator that issues the profile.</p>
<figure><img loading="lazy" decoding="async" src="https://media.spenza.com/wp-content/uploads/2026/11/iot-sim-profile-swap-orange.webp" alt="A chunky eUICC chip holding three cream profile cards while a new profile card arrives on a ribbon from a cell tower" width="1600" height="900" loading="lazy"><figcaption>The eUICC stays in the device; the operator profile inside it is what changes.</figcaption></figure>
<p>An eUICC can be soldered to a board or supplied as a removable card. Packaging and remote capability are separate properties, so a removable card is not automatically unable to take remote profiles, and a soldered chip is not automatically manageable by your platform. For an original equipment manufacturer (OEM), the practical gain is fewer connectivity changes that need physical access. The work moves to firmware integration, connectivity recovery and operations tooling, and a dashboard button does not remove those dependencies.</p>
<div class="mh-callout"><p><strong>Key takeaway.</strong> Buy a supported end-to-end workflow, not a label. &ldquo;eSIM compatible&rdquo; does not say which profiles, commands, networks or recovery options a device supports.</p></div>
<h2 id="rsp-architectures">Which RSP architecture applies: SGP.22, SGP.32 or SGP.02?</h2>
<p>GSMA publishes three provisioning architectures, and components with similar jobs are not interchangeable between them. The first question for any project is which family your device belongs to.</p>
<div class="mh-table"><table><thead><tr><th>Family</th><th>Device-side role</th><th>Server-side roles</th><th>Typical fit</th></tr></thead><tbody><tr><td><strong>SGP.22</strong>, consumer</td><td>Local Profile Assistant (LPA) handles local profile download and user interface</td><td>SM-DP+ prepares and delivers profiles; SM-DS can point the device to the right SM-DP+</td><td>Phones, tablets, wearables and other devices with an end user present</td></tr><tr><td><strong>SGP.32</strong>, IoT</td><td>IoT Profile Assistant (IPA), located in the device (IPAd) or in the eUICC (IPAe)</td><td>eSIM IoT remote Manager (eIM) manages operations remotely; SM-DP+ supplies profiles</td><td>Unattended or user-interface-constrained devices such as meters, trackers and gateways</td></tr><tr><td><strong>SGP.02</strong>, legacy M2M</td><td>eUICC takes part in a machine-to-machine architecture</td><td>SM-DP prepares profiles; SM-SR (Secure Routing) manages the eUICC</td><td>Existing M2M deployments that predate SGP.32</td></tr></tbody></table></div>
<p>Sources: GSMA <a href="https://www.gsma.com/solutions-and-impact/technologies/esim/wp-content/uploads/2023/12/SGP.22-v3.1.pdf" rel="noopener" target="_blank">SGP.22 v3.1</a>, <a href="https://www.gsma.com/esim/wp-content/uploads/2022/04/SGP.31-v1.0.pdf" rel="noopener" target="_blank">SGP.31 v1.0</a> and <a href="https://www.gsma.com/solutions-and-impact/technologies/esim/wp-content/uploads/2024/06/SGP.32-v1.2.pdf" rel="noopener" target="_blank">SGP.32 v1.2</a>. The table summarizes roles, not every interface.</p>
<figure><img loading="lazy" decoding="async" src="https://media.spenza.com/wp-content/uploads/2026/11/m2m-esim-standards-fork-orange.webp" alt="A signpost with SGP.02, SGP.22 and SGP.32 arrows at a fork in a cream road that leads to a smartphone, a car and a small connected IoT device" width="1600" height="900" loading="lazy"><figcaption>Pick the family first; the components that follow depend on it.</figcaption></figure>
<h3 id="consumer-lpa">Consumer devices: the LPA</h3>
<p>In SGP.22 the LPA is a functional element in the device or in the eUICC that downloads profiles and presents the user interface. The standard builds in end-user intent and an optional confirmation code from the operator, because a person is expected to be present. That assumption is exactly what fails on a roadside sensor.</p>
<h3 id="iot-eim-ipa">IoT devices: the eIM and the IPA</h3>
<p>SGP.31 sets the architecture and requirements for remote provisioning of eUICCs in network-constrained or user-interface-constrained IoT devices, and SGP.32 is the technical specification that implements it. The eIM is the remote manager. It holds the right to send profile state management operations such as enable, disable and delete, and the eUICC authenticates it using eIM configuration data. The IPA is the device-side counterpart, and SGP.32 requires it to sit either in the device or in the eUICC.</p>
<p>SGP.32 keeps SM-DP+ for profile preparation, so consumer and IoT paths share infrastructure, but it does not pair an LPA with an eIM. Profile download can be direct, with the IPA talking to the SM-DP+, or indirect, with the eIM relaying the package to the IPA. Which one your device can use depends on the IPA capabilities it implements. Our <a href="/esim/sgp-22-vs-sgp-32-esim-standards-guide/">SGP.22 vs SGP.32 comparison</a> develops the choice in more detail.</p>
<h3 id="legacy-m2m">Legacy M2M: SGP.02</h3>
<p>SGP.02 predates SGP.32 and uses an SM-SR to route management commands to the eUICC. Many deployed IoT fleets run on it. If you operate one, find out who controls the SM-SR relationship before planning a move, since that decides who can authorize changes. The <a href="/iot/what-is-m2m-machine-to-machine-sims/">M2M SIM explainer</a> gives background on that generation.</p>
<h3 id="record-versions">Record versions, not just names</h3>
<p>The specifications are versioned and the GSMA keeps a <a href="https://www.gsma.com/solutions-and-impact/technologies/esim/esim-specification/" rel="noopener" target="_blank">register of consumer and IoT specification versions</a> with their status. The documents this guide checked were SGP.22 v3.1 (1 December 2023), SGP.31 v1.0 (19 April 2022) and SGP.32 v1.2 (27 June 2024); newer versions may exist. Record the exact version each supplier implements for the device, eUICC and server. A procurement label is not an interoperability result.</p>
<h2 id="how-rsp-works">How does remote SIM provisioning work?</h2>
<p>RSP starts with an authorized profile request and a usable communication path. The participants authenticate each other, the protected profile is delivered and installed, and the result is reported. Enabling the profile, registering on the network and reaching your application are further outcomes that your deployment must verify separately.</p>
<ol><li><strong>Identify the target.</strong> Tie the device record to its eUICC identifier (EID), the intended service and the profile it is allowed to receive. Keep customer and device identifiers distinct.</li><li><strong>Establish connectivity.</strong> Provide a bootstrap profile or another path, such as Wi-Fi where the device supports it, and confirm the provisioning endpoints are reachable.</li><li><strong>Authorize the operation.</strong> Check assignment, permissions and profile availability before sending the request. Consumer approval and remote IoT management follow different rules.</li><li><strong>Download and install.</strong> Record the outcome the provisioning stack reports, along with the operation identifier and any error.</li><li><strong>Enable and confirm service.</strong> Check the profile state, network registration and the data or voice service you need. Installation alone is not enough.</li><li><strong>Reconcile the business record.</strong> Match confirmed service to the right customer, plan and billing start, and investigate differences.</li></ol>
<figure><img loading="lazy" decoding="async" src="https://media.spenza.com/wp-content/uploads/2026/11/rsp-bootstrap-to-operational-profile-orange.webp" alt="A cream profile card on a ribbon coming from a cell tower toward a charcoal chip with gold contacts, labelled Profile and Bootstrap." width="1600" height="900" loading="lazy"><figcaption>A bootstrap path lets the device reach the server that delivers the operational profile.</figcaption></figure>
<h3 id="bootstrap">Bootstrap and operational profiles</h3>
<p>A device with no working subscription needs some way to reach the server that holds its profile. That is the job of a bootstrap connection, which can be a small profile pre-installed for the purpose or another supported path. SGP.22 uses the term Provisioning Profile for a profile that supplies connectivity for provisioning purposes and keeps it out of the end user&rsquo;s profile list. Its coverage, permissions and allowance decide whether remote setup succeeds in the field, so test it in the countries where the device will first power on. For the multi-network case, see how <a href="/esim/deploy-multi-network-esim-rsp-aggregation/">RSP aggregation across networks</a> is deployed.</p>
<h3 id="activation-methods">Activation on phones</h3>
<p>On a supported phone, activation may use a carrier assignment, transfer, link, app, QR code or manual entry. <a href="https://support.apple.com/en-us/118669" rel="noopener" target="_blank">Apple&rsquo;s eSIM setup page</a> lists these methods for iPhone and notes that availability depends on the carrier. A QR code is therefore one delivery mechanism, not the definition of RSP.</p>
<h3 id="unattended">Unattended devices</h3>
<p>For equipment nobody touches, record when the device can communicate and how the management system learns that an operation finished. A queued request must not appear as a successful activation in support or billing. Decide which system is the authority for each state change, and keep that rule in the runbook.</p>
<div class="mh-table"><table><thead><tr><th>Check</th><th>Required outcome</th></tr></thead><tbody><tr><td>Profile</td><td>Installed and enabled as intended</td></tr><tr><td>Network</td><td>Registered with the approved service</td></tr><tr><td>Application</td><td>Data reaches the intended endpoint</td></tr></tbody></table></div>
<p>Accept working service only when all three rows pass. A successful download proves one part of readiness.</p>
<h2 id="what-to-plan-for">What should you plan for before choosing a platform?</h2>
<h3 id="cost">Cost and effort</h3>
<p>RSP shifts effort from physical SIM handling toward device integration, platform operations and recovery testing. Savings depend on how many site visits, shipments and SIM swaps you actually avoid, set against the price of the provisioning service and the engineering to integrate it. Ask each supplier for the inputs below rather than comparing a single headline rate; no universal RSP price applies to every fleet.</p>
<div class="mh-table"><table><thead><tr><th>Item</th><th>Input to collect</th><th>Owner</th></tr></thead><tbody><tr><td>Physical handling</td><td>Shipping, stocking and site-visit costs you would avoid</td><td>Operations</td></tr><tr><td>Device integration</td><td>Module, firmware and provisioning-stack work</td><td>Product engineering</td></tr><tr><td>Platform service</td><td>Setup, per-profile, per-operation and recurring fee units</td><td>Procurement and supplier</td></tr><tr><td>Connectivity</td><td>Bootstrap and operational allowances, coverage and restrictions</td><td>Connectivity owner</td></tr><tr><td>Exceptions</td><td>Support time, recovery work and replacement procedure</td><td>Delivery and support</td></tr></tbody></table></div>
<p>Model total cost as connectivity plus provisioning service, integration, support and any remaining physical intervention, over the same period and active fleet for every quote. A per-profile price and a per-active-device price have different denominators, so multiplying both by shipped units can distort the comparison. Our <a href="/telecom/iot-connectivity-cost-guide-2025/">IoT connectivity cost guide</a> covers the connectivity side. For a mixed estate, separate staff phones from unattended equipment; the <a href="/esim/esim-for-enterprises-business-enabler-2025/">enterprise eSIM guide</a> helps assign those responsibilities.</p>
<h3 id="security">Security and permissions</h3>
<p>The specifications protect profile delivery and management, but deployment security also depends on who can request changes and how credentials are handled. Restrict destructive actions such as disabling or deleting a profile, and separate routine support access from bulk administration. Keep an audit trail linking operator, target, requested change and confirmed outcome, and keep activation secrets out of ordinary support notes. SGP.31 itself lists accidental profile disabling or deletion that leaves a device without connectivity among the threats the architecture must address, which is a good reason to gate those commands.</p>
<div class="mh-callout"><p><strong>Watch out.</strong> Having a profile available locally does not settle roaming restrictions, identity requirements, privacy duties or whether you may offer service in a country. Confirm those with the carrier and your advisers before deployment.</p></div>
<h3 id="recovery">Failure and recovery</h3>
<p>A replacement profile can install successfully and still fail to carry traffic. Test the recovery mechanism before any fleet-wide change. SGP.31 defines a roll-back mechanism for IoT devices: if communication between the eIM and the IPA cannot be established using the newly enabled profile, the previously enabled profile is enabled again. SGP.32 carries a rollback flag on the enable operation and a matching eUICC function. Whether your device and platform implement it is something to confirm, not assume.</p>
<figure><img loading="lazy" decoding="async" src="https://media.spenza.com/wp-content/uploads/2026/11/multi-carrier-iot-failover-profiles-orange.webp" alt="A cream delivery truck carrying a charcoal tracker between two cell towers on separate hills, the left one labelled Primary with a wrench badge and the right one labelled Backup and glowing, joined by cream ribbons" width="1600" height="900" loading="lazy"><figcaption>Failover to a backup network only works if a working profile for it is already on the eUICC.</figcaption></figure>
<p>When an outcome is unknown, inspect the current state before retrying. A timeout can hide a completed action, and a blind retry or an early delete of the old profile can turn a recoverable incident into a truck roll. Define who can intervene when the device cannot be reached, and what evidence closes the incident.</p>
<h2 id="rollout-checklist">How to roll out RSP: an acceptance checklist</h2>
<p>Run a representative pilot before the fleet. It should cover the real hardware, firmware, target networks and failure conditions, and each result needs an owner and retained evidence so that provisioning success is not confused with network availability or application readiness.</p>
<div class="mh-table"><table><thead><tr><th>Test</th><th>Evidence to retain</th><th>Acceptance owner</th></tr></thead><tbody><tr><td>Supported combination</td><td>Device, eUICC, firmware, IPA or LPA and server versions</td><td>Engineering</td></tr><tr><td>Initial provisioning</td><td>Bootstrap reachability, requested profile and installation outcome</td><td>Delivery</td></tr><tr><td>Working service</td><td>Profile state, network registration and an application transaction</td><td>Network and application teams</td></tr><tr><td>Interrupted operation</td><td>Observed state, safe retry or recovery, escalation record</td><td>Support engineering</td></tr><tr><td>Commercial handoff</td><td>Correct customer, plan and billing start</td><td>Operations and finance</td></tr></tbody></table></div>
<p>Choose the consumer path when the product and its activation experience fit that architecture. Choose the IoT arrangement when the equipment is unattended or constrained and the complete stack is supported. Leave an existing SGP.02 deployment alone until its migration and ownership questions are answered. Use the <a href="/esim-compatibility-checker/">eSIM compatibility checker</a> for first screening, then get supplier confirmation for your exact firmware and profile combination; a model-family match is not a tested one.</p>

The policies that decide which profile a device should hold, and when to switch, sit in an orchestration layer described in our <a href="/esim/esim-orchestration-global-iot/">eSIM orchestration guide</a>, and fleet visibility across carriers is covered in the <a href="/telecom/single-pane-of-glass-iot-connectivity-management/">single-pane-of-glass connectivity management</a> article. If you plan to launch your own branded mobile service on eSIM, see the <a href="/mvno/mvno-esim-implementation/">MVNO eSIM implementation guide</a>. To compare platforms, start with the <a href="/esim/leading-iot-connectivity-management-platforms/">connectivity management platform comparison</a>.</p>

<h2 id="conclusion">Conclusion: choose the workflow you can verify</h2>
<p>Remote SIM provisioning is useful when it removes a physical dependency without creating an invisible operational one. Start with the device and the service it must deliver, pick the matching architecture from SGP.22, SGP.32 or SGP.02, and prove every transition through to the application. Keep failed or uncertain outcomes visible until an owner resolves them, and compare cost on identical fleet and period assumptions. The next step is a scoped pilot with agreed evidence and recovery criteria, run before you promise activation times to customers.</p>
